## Session Notes

- After generating a new lib (or otherwise changing project dependency edges — including a project's _first_ import of an existing lib, e.g. wiring `ghost-ai-components` into `apps/ghost-ai`), run `npx nx reset` before relying on `nx run-many`/Tailwind's `createGlobPatternsForDependencies` — the cached project graph the dev server's Tailwind config reads (`readCachedProjectGraph()`) does not pick up the new/changed dependency edge otherwise, so the lib's classes silently don't make it into the Tailwind content scan even after restarting `next dev` and clearing `.next`. `nx reset` alone isn't enough — it clears the cache but doesn't repopulate it (`createGlobPatternsForDependencies` then errors with "No cached ProjectGraph is available" and silently returns `[]`); follow it with any command that recomputes the graph (e.g. `npx nx show projects`) before starting the dev server. Confirmed twice now; not a Turbopack bug, just a stale-graph gotcha. Also run `npx nx sync` after the new import so TS project references stay accurate (it had been silently warning "workspace out of sync" since the import predated the reference).
- The workspace-wide `shadcn-util:build` / `shadcn:build` nx targets currently fail (`error TS5072: Unknown build option '--useLegacyTypescriptPlugin=true'`) due to `nx.json`'s `targetDefaults.build.options.useLegacyTypescriptPlugin: true` being incompatible with the installed TypeScript version. Worked around it by building those libs directly with `npx tsc --build <tsconfig.lib.json> --force` instead of going through the nx target. Pre-existing, unrelated to this unit's work — not fixed. This same `useLegacyTypescriptPlugin` flag is also on `ghost-ai`'s own `build`/`test` targets, so `nx run ghost-ai:build` and `nx run ghost-ai:test` fail immediately on the `^build` dependency before ever reaching the app. Worked around for verification by running the underlying commands directly instead (`cd apps/ghost-ai && npx next build`, `cd apps/ghost-ai && npx jest --config jest.config.cts`) after building `shadcn-util`/`shadcn`/`ghost-ai-components` via `tsc --build --force` first — `tsconfig.base.json`'s path aliases point straight at lib `src/`, so app compilation doesn't actually need the prebuilt `dist/` output, only the lib's own `.d.ts` build for project-reference resolution.
- `nx run ghost-ai:lint` also currently fails standalone (`ESLint: "overrides" key... not supported in flat config`) — pre-existing in the app's own eslint config, unrelated to this unit's work.
- Under this app's Next.js/Turbopack + Tailwind v3 PostCSS setup, `tailwindcss`'s `normalizeTailwindDirectives` check runs per-file, not on the post-`@import` merged result: a CSS file using `@layer base { ... }` throws `@layer base is used but no matching @tailwind base directive` even if a file it `@import`s already has `@tailwind base`. `apps/ghost-ai/src/app/global.css` only `@import`s `libs/shadcn-util/src/global.css` (which has the `@tailwind` directives) and doesn't declare its own, so anything added there needs to avoid `@layer` — bare `@apply`/plain rules work fine outside a `@layer` block.
- `npx next build` (run directly, per the `useLegacyTypescriptPlugin` workaround above) currently always fails at its own internal "Running TypeScript..." step with `File '.../libs/shadcn/src/index.ts' is not under 'rootDir' '.../apps/ghost-ai/src'` (triggered via `apps/ghost-ai/src/app/editor/page.tsx`'s `@org/shadcn` import chain), plus a `⚠ TypeScript project references are not fully supported` warning right before it — Next's own bundled type-checker doesn't fully honor the app tsconfig's `references` array the way plain `tsc --noEmit -p tsconfig.json` does, and `shadcn` (unlike the other libs) sits outside `apps/ghost-ai/src`'s `rootDir` with no dist build of its own. Pre-existing (confirmed by stashing an entire unit's changes and re-running — identical failure, identical file/line), not caused by any single unit's work, and not fixed. Turbopack's own bundling/compiling step (`✓ Compiled successfully`) reliably still succeeds before this point, so `npx next build`'s compile phase remains a valid signal for "does this unit's code bundle correctly" even though the overall command's exit code will stay non-zero until someone fixes this `rootDir` mismatch — the more reliable per-unit check is `cd apps/ghost-ai && npx tsc --noEmit -p tsconfig.json` (plain `tsc`, no project-references quirk) plus watching for `✓ Compiled successfully` in the `next build` output.
